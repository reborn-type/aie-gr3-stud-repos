## 2. Постановка задачи и контекст

Опишите:

1. **Предметную область и задачу:**
   - Пытаюсь решить задачу классификации. 
   - Потенциальный пользователь - человек направляющий обращение в поддержку банка, а также сотрудник который должен получить и решить это обращение. 

2. **Формулировку задачи в терминах ML/ИИ:**
   - На входные данные приходит title и text, которые потом совмещаются и передаются на вход обученной модели. 
   - Целевой переменной является label, на выход модели приходит конкретный отдел, который потом на фронтенде трансформируется в человеческий язык. 
   - Есть требование к скорости и точности, обращение должно быть быстро и корректно назначено на отдел. Но при этом есть проблема с данными, так как в свободных открытых источниках очень мало подходящих датасетов для обучения модели в данной области. 

3. **Целевые метрики качества:**
   - Для оценки модели использую метрики: accuracy, f1_macro и f1_weighted.
   - accuracy важно для отображения процента корректно-классифицированных обращений, f1_macro для обычного среднего по классам, f1_weighted для среднего с учетом размера классов.

## 4. Модели и подходы

Опишите, какие модели вы пробовали и как развивался ваш подход:

1. **Базовые (baseline) модели:**
   - В качестве baseline я использовал TF-IDF векторизацию + логистическую регрессию
   - По ключевым метрикам они показали: 
   accuracy                           0.93       250
       macro avg       0.94      0.93      0.93       250
    weighted avg       0.94      0.93      0.93       250


2. **Улучшенные модели и эксперименты:**
   - в качестве основной модели была выбрана предобученная DeepPavlov/rubert-base-cased-conversational, взятая с HuggingFace, и к ней был сделан fine-tuning
   - Важными параметрами стала max_length и batch_size, так как при больших значениях данная не могла обучиться, не хватало места в оперативной памяти ноутбука. 
   - В качестве экспериментов пробовал менять гиперпараметры обучения, увеличивать lr, batch_size 

3. **Нейросетевые модели (если применимо):**
   - В качестве архитектуры использовалась BERT для классификации последовательностей. 
   - Батчи были в области от 2 до 8, на размерах батча 8 иногда в ноутбуке не хватало оперативной памяти для дообучения модели (тренировал модель с этими параметрами в `exp02_fine_tuning_params.ipynb`), lr был в диапазоне от 3e-5 до 5e-5.

## 6. Архитектура решения и сервис

Опишите, как из модели получился работающий сервис:

1. **Архитектура пайплайна:**
   - Сначала грузяться данных и происходит их предобработка (проверка на пропуски, дубли и тд), далее данные разделяются на train/val/test, потом текст токенизируется и подается на вход fine-tuning для улучшения RuBERT, далее оценивается качество модели, после она сохраняется в artifacts, потом из artifacts она выгружается при старте серверной части приложения, происходит инференс через API и отображает результаты на frontend.

   1. Датасет
   ↓
   2. Предобработка данных
   ↓
   3. Разделение на train / validation / test
   ↓
   4. Токенизация текста
   ↓
   5. Fine-tuning RuBERT
   ↓
   6. Оценка качества модели
   ↓
   7. Сохранение модели в artifacts
   ↓
   8. Загрузка модели при старте backend
   ↓
   9. Инференс через API
   ↓
   10. Отображение результата на frontend

2. **API и endpoints:**
   - реализованы endpoints: POST /predict, GET /health, DELETE /, GET /{appeal_id}, DELETE /{appeal_id}, при этом всем, у всех эндпоинтов по умолчанию идет префикс /appeals, кроме health. 
   - `/predict` принимает параметры: `title` и `text`, возвращает title, text, department, percent_of_confidence

3. **Технологический стек:**
   - Используются такие библиотеки и фреймворки как: FastAPI, Alembic, Pydantic, matplotlib.pyplot, pathlib, typing, datasets, numpy, sklearn, torch, pandas, pytest, types. Для фронтенда используется: React + Vite, axios, module.css; 
   - docker-compose используется для быстрого запуска приложения, для того чтобы запустить, нужно создать .env в configs/ с DB_URL, а после находясь в папке backend , в терминале написать `docker compose up --build`, docker сам поднимит фронтенд, бекенд и базу данных

## 8. Ограничения и дальнейшая работа

Будьте честны:

- У проекта есть ограничение в качестве из-за обьема и качества данных подаваемых на вход, в датасете мало пограничных случаев и нестандартных ситуаций, из-за этого модель может неправильно назначать на пограничных случаях, также к этому модель редко на много процентов уверена что назначает правильно. Также можно было бы добавить отслеживание метрик при создании обращения. 
- что бы вы сделали, если бы было больше времени:
  - Расширил бы датасет вручную добавив большое количество пограничных случаев, поскольку ии агентами не получилось расширить датасет качественно, пришлось бы делать это вручную. Добавил бы в датасет спорные случае, конфликты и прочие обращения которые помогли бы модели лучше обучится. 
  - Добавил бы дополнительный React route для отслеживания метрик по обращениям, тобеж отображал бы не только confidence но и другие дополнительные метрики, например: ближайшие по confidence отделы, схожие документы из датасета. 
  - Добавил бы возможность самому вручную выбрать отдел, в случае если на отличных, качественных данных, у модели все равно остается сомнения и образно остается у нас 2-3 отдела которые наиболее веротяны, дал бы возможность пользователю самому выбрать нужный отдел для очень пограничного случая.
